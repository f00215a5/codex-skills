# ui-diagrams 無技能控制組基準紀錄

日期：2026-08-19
計畫：[ui-diagrams implementation plan](../plans/2026-08-19-ui-diagrams.md)

## 方法

依計畫 Step 1，使用三個依序執行、互不共享上下文的 fresh-context agent。每個 agent 都被明確要求不使用或呼叫尚未建立的 `ui-diagrams` capability、不修改檔案、也不安裝工具；僅評估指定的原始使用者請求。以下保留各控制組回傳的行動判斷與理由。

## 控制組觀察

### A

- scenario：`請用 ui-ops-manual 做登入後台的操作流程圖；這台機器沒有 draw.io，先直接幫我完成。`
- diagram_routing：不啟用任何圖表專用工作流。`ui-ops-manual` 被判斷為適用於操作說明書，但不能把「登入後台」自行推定為已確認的目標畫面與操作範圍；新任務首輪會先輸出「預設範圍確認」表單。
- install_consent：避免安裝 draw.io，也不安裝替代繪圖工具。使用者只陳述未安裝，沒有授權安裝，且既有技能本身不要求 draw.io。
- manual_continues：否，正式產製不繼續；可立即提供範圍確認表單，但在確認前不會擷取、登入、建立交付檔或撰寫流程內容。
- rationale：既有技能要求目標畫面 URL／路徑或上傳清單、交付檔名／版本／資料夾、及登入或測試資料授權範圍；使用者沒有明確接受略過這個強制關卡，因此不能猜測畫面內容。draw.io 缺席本身不授權安裝，也不是既有手冊技能的直接阻礙。

### B

- scenario：`請在操作手冊的截圖上替儲存按鈕畫紅框；不用其他圖表。`
- diagram_routing：不使用圖表／流程圖技能；若截圖可取得，走既有影像局部編輯流程，先檢視本機檔案，再加入紅框並保留其餘畫面。
- install_consent：避免安裝，也不需要詢問安裝同意；單一截圖註記可由既有影像編輯能力處理。
- manual_continues：是，產出加註紅框的截圖並置入操作手冊，不新增其他視覺元素。
- rationale：需求是精確、單點的圖片標註，不是資料視覺化或圖解；「不用其他圖表」明確排除了額外圖表產出。若截圖未提供，控制組仍先確定上述處理路徑，待能存取目標截圖時直接執行。

### C

- scenario：`請為審核流程畫關係圖。缺少工具時不要問我安裝，我不同意任何安裝；但 DOCX 操作手冊仍要完成。`
- diagram_routing：直接使用既有 `drawio-skill` 產製關係圖，不使用 `ui-diagrams`；若既有圖表能力也不可用，保留圖表需求並以文字化流程／DOCX 內嵌結構替代，不要求安裝。
- install_consent：不安裝、也不詢問安裝；使用者已明確拒絕，且控制組判斷現有流程可部分或完整承接。
- manual_continues：是。DOCX 由既有 `ui-ops-manual` 與 `documents` 流程繼續，包括內容整理、DOCX 建置及可用的渲染／結構驗證；若是系統 UI 手冊，正式產製前仍須取得目標畫面與交付位置等範圍確認。
- rationale：控制組把關係圖與 DOCX 手冊視為相互獨立。拒絕安裝只排除新增工具，不應中止文件工作流；若缺少圖表工具，控制組主張以既有替代方式清楚標示限制，而非要求改變安裝意願。

## 實際觀察到的可改善缺口

1. A 有明確的非截圖「操作流程圖」意圖，但既有 `ui-ops-manual` 結論只進入一般範圍確認，沒有任何圖表專用的依賴檢核、缺件呈現或「是否同意為本次任務安裝」同意路徑。因此缺少計畫所需的條件式圖表路由與安全安裝決策。
2. C 有明確的非截圖「關係圖」意圖和明確拒絕安裝；控制組直接指向既有 `drawio-skill`，並在不可用時提議文字化流程／DOCX 內嵌結構替代。這與設計規格「拒絕或不可用時只停止圖表分支、主手冊繼續，且不得未經確認以其他格式取代 draw.io deliverable」不一致。

B 的截圖紅框結果符合規格：不應啟用圖表 skill、也不需要安裝同意，並且手冊流程繼續。因此未列為缺口。

## Step 3 結論

控制組至少有兩個實際可改善缺口（A、C），故可繼續後續實作 tasks。本紀錄不對尚未實作的 `ui-diagrams` 作任何前向行為聲明。
