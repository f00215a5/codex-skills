# 截圖完整性與缺件處理

在第一張畫面取證前閱讀。此規格適用於整本或局部修訂手冊，沿用本次已確認範圍；使用者已在目前任務接受預設或明示略過範圍確認時，不重複要求核准已授權的必要工作。範圍、語意與資產台帳沿用同一份 QA record，依 [incremental-qa-workflow.md](incremental-qa-workflow.md) 回填，不另造重複 gate。

每張圖的 manifest schema、capture state 綁定、DOM／文字 Range 測量、CUA bytes 落地和唯讀驗證命令見 [references/screenshot-manifest.md](screenshot-manifest.md)。

## 開工盤點與最小代表案例矩陣

在取證前先建立矩陣骨架：功能、主配置區、子配置區、會造成獨特操作的條件／狀態、候選代表案例、證據來源與狀態。選代表案例前先從實機導覽、主配置頁與可到達的子 Tab／設定清單列出候選項目；最小案例只能合併已證明相同的重複流程，不能省略主／子配置區。以實機 UI 確認部署中的畫面；提供的前端原始碼只用來找候選路由／元件／條件，本機程式碼不是部署事實，衝突時記為 `unknown`／「待確認」。取證後把 `captureState.id`、manifest source 與欄位語意回填同一矩陣及唯一 inventory，呼叫 builder 前完成必要核對。

用最小案例集合覆蓋每個獨特控制項、條件狀態及成功／失敗結果。共用流程只放一處；不同配置以差異表描述不同欄位、條件或結果，只有狀態、權限、資料或結果真的不同才新增主圖。資料筆數、頁數、圖片數量或「每種類型一張」不是完成標準；同一狀態的相同頁面不重複拍攝，必要時在同一主圖下重用 caption／步驟對應。主要主／子配置區沒有畫面、控制項或操作證據是缺件，不能自行改列為 `accepted limitation`。

## 先跑通一張，再批量產製

代表圖校準、小批次 gate、finding ledger 與資產失效規則見 [incremental-qa-workflow.md](incremental-qa-workflow.md)；本規格仍定義每張圖的完整性與缺件判定。

完成範圍及 CJK renderer 預檢後，選一張包含實際操作目標、頁面上下文及需隱碼資料的代表性頁面，完成以下實測；沒有敏感資料時記錄該事實，不捏造遮蔽項目：

1. 以當前工具支援且政策允許的方式取得完整實機截圖，確認本機來源檔可讀、尺寸正確。若 CUA 契約回傳 `Uint8Array`，在同一 Node runtime 以 `fs/promises.writeFile` 寫入受限 QA 路徑；先查實際契約，不猜測 API，也不以生成 UI 代替截圖。
2. 依 screenshot-redaction-policy 精準隱碼並扁平化，保留完整畫面。
3. 在同一張完整圖加入操作紅框與編號，直接檢視原圖、隱碼圖及標註圖，確認位置與文字。
4. 為這張圖各自建立 manifest，執行 [screenshot-manifest.md](screenshot-manifest.md) 的 `validate_screenshot_manifest.py` 命令；再以已選定 renderer 嵌入暫存 DOCX 並實際檢視，確認讀者在成品縮放下仍能辨識完整頁面、操作位置與圖說。必要 detail 只能補充同一狀態主圖，不能取代主圖。

這張圖只證明處理流程可用，不能代表其他功能也已完成。流程未跑通前先解決失敗點，勿大量生成缺圖文件後才處理截圖。

## 完整頁面主圖

- 每個操作畫面的主圖預設是**整個應用程式頁面**：保留頁首／頁面標題、導覽／側邊欄（原畫面存在時）、主要內容與操作區域的相對位置。瀏覽器網址列或作業系統桌面不是必要內容。
- 短頁面使用完整 viewport；可捲動頁面不能把第一個 viewport 冒充整頁。優先使用工具支援的 full-page 擷取；內部捲動面板或長頁無法一次正確擷取時，使用有重疊區域、順序及位置說明的連續完整 viewport，覆蓋相關頁面內容。巢狀垂直／水平捲動容器要分別確認可到達內容、捲動位移與連續畫面的重疊；確認固定頁首、浮層與捲動容器沒有重複、消失或錯位。
- full-page 截圖可能重新排版、改變 lazy content 或讓 fixed header 覆蓋內容；不能把拍攝前 DOM 座標直接當成 PNG 座標。每張 raw 拍完後逐張在 100% 做 pixel-level 對照，確認頁首、固定元素、每個敏感值和每個操作目標的實際位置，再生成該張 redacted／annotated manifest。
- 若 full-page 擷取造成重排、固定元素覆蓋或文字不可讀，改用有明確順序、scroll offset、重疊區域和每張個別 manifest 的 `viewport-sequence`；每個 viewport 都要直接檢視並重新測量，不能用第一張的列距批量套用。每張圖都要逐一查找頁首、摘要、列表、麵包屑、彈窗背景等重複出現的敏感值並重新遮蔽；`fullPage` 參數或 `captureKind` 字串本身不能代替內容完整性確認。
- 彈窗保留其所在的頁面背景及完整彈窗；內部內容過長時按上述方式補連續畫面。不得只裁切一個欄位、按鈕或錯誤訊息作為唯一操作圖。
- 主圖上以紅框標示本步驟操作區／控制項，使用編號對應文字步驟；一張圖過密時拆成多張有完整頁面脈絡的操作圖。局部放大圖只能補充主圖，須標明對應圖號與區域，不能取代主圖或用來規避隱碼。
- 長頁縮進 Word 後字太小時，採用連續畫面分頁、橫式頁面或「完整主圖＋局部放大」，不得為了塞進一頁而裁掉定位資訊。需直接檢視最終文件中的可讀性。

## 隱碼或擷取失敗的處理

「目前無法隱碼」是待排除的問題，不是移除截圖要求或縮減範圍的授權。依實際錯誤定位層級並保留不含敏感值的證據：

| 失敗點 | 下一步 |
| --- | --- |
| 截圖未落地或本機檔案不可讀 | 查閱正在使用的工具契約，核實支援的擷取、保存／匯出方式和回傳路徑；用可寫入的受限 QA 路徑重試。不得杜撰 API，也不得繞過瀏覽器工具的存取限制。 |
| 影像套件、座標或格式錯誤 | 用已授權且可用的影像處理能力對本機副本完成像素遮蔽，修正格式／倍率／函式用法，再直接檢視。不得以生成或重繪 UI 代替實機證據。 |
| 敏感值太多或遮蔽影響閱讀 | 精準遮蔽值、保留欄名與位置；可改取已授權的測試資料或不含敏感值的真實畫面狀態，但必須仍符合該步驟。不可偷偷換成空白／無結果狀態描述成功查詢。 |
| 嵌入或渲染後不正確 | 回到已通過的圖片與 DOCX 排版查因，修正後重跑；renderer 備援仍遵守 safe-word-render-policy。 |

每次重試應針對新證據修正，不無限重跑同一失敗命令。不為取證自行修改業務資料或放寬隱碼、權限與 renderer 政策。確實需要額外權限、測試資料或外部協助時，說明已嘗試方式、具體阻礙及最小需要的協助；用可用且契約允許的提問工具取得必要輸入，繼續不受阻礙的工作。不得只回覆「無法隱碼」便交付無圖文件。

若瀏覽器／Word 工作在受限沙箱中出現 access denied，依 [render-and-annotation-qa.md](render-and-annotation-qa.md) 的分類，先在可寫入工作區重試；Word 的沙箱拒絕不是自動改用 fallback 的理由，必要時須在已授權的本機互動環境重試。這項限制不會減少已確認的截圖覆蓋要求。

## 覆蓋清單與完成條件

在 QA 工作區保存與已確認功能清單逐項對應的覆蓋表（Markdown 或 JSON 均可）：功能 ID、章節、必要操作／狀態、完整頁面圖片、補充局部圖、標註 manifest、最終文件位置、隱碼／標註／渲染／審核狀態及缺件原因。圖片 manifest 同時標示 `captureKind`（`full-page`、`viewport-sequence` 或 `detail`）、所屬功能與狀態；`detail` 必須指向其完整主圖。連續 viewport 記錄順序與捲動位置。

進入建置前，覆蓋表中的每個欄位、表頭、必填標記與可見選項都要能回指目前 capture 的 `captureState.id` 和 manifest `source`；`captureState` 要核對當下可見視窗、載入完成／資料狀態與目標控制項，未開啟的視窗或表單不得以名稱代稱；只列出實際看見的項目。用途按該畫面具體記錄，不能用整表相同的泛用句代替；必填狀態未能由證據確認時寫「待確認」，不能填「否」。每張 annotated 圖的圖說編號在該圖內須唯一，並與目前 manifest 的 annotation id 一一對齊。

manifest 的 `pending` 是預覽／待人工檢視狀態；validator 可回報 `geometry_status: "pass"`，但 `manifest_status` 不得為 `pass`。builder 必須逐張檢視並更新狀態，獨立 reviewer 仍依交付規範直接檢查完整證據。

- 比對整份確認清單，不以「有圖片」、圖片數量、代表性樣本或只審核已嵌入圖片作為完整性證明。數個步驟可共用一張適用主圖，但每項必要操作／狀態都要有可追溯對應。
- 缺少要求的主圖、必要狀態或完整性覆蓋時，返回擷取／建置流程補齊。不得自行把全功能手冊改成三張圖的補充版，或把必要截圖列成可選 follow-up 再問是否要做。
- 第二輪沿用已確認範圍與代表案例矩陣；hash、capture state 和依賴均未變，且 baseline 的語意項目已通過或使用者明示接受的資產，才可承接原語意結果，並在 QA record 記為 `inherited` 及理由。上一輪 `fail`／`blocked`／`pending` 或未解項目不可承接。每輪仍檢查全部最終渲染頁的版面；版型或其他全域版面變更時，所有頁面列為受影響並重新檢查。
- `draft`／`blocked` 用於如實記錄中間狀態，**不是完成條件，也不是停止已授權工作的理由**。使用者明確要求先收草稿，或遇到有證據且目前無法排除的外部阻礙時，才可交接未完成版本，須列已完成／要求總數與缺件，不能宣稱已完成原需求。
- 首輪或範圍重建時，最終獨立審核必須同時檢查覆蓋表、全部主圖及最終渲染頁面；後續 delta review 仍檢查完整覆蓋表與全部最終版面，對未變且 hash／依賴可驗證的主圖承接語意結果，對 changed／affected 主圖直接重審。只檢查少量已嵌入的圖，不足以通過全功能手冊。機械結構檢查不能證明頁面完整、隱碼或紅框語意。
- 交付目錄依使用者提供的路徑逐層建立並核對，不把 `日期\子資料夾` 改成 `日期_子資料夾`。原始證據留在受限 QA 工作區，交付資料夾只放本次核准的交付檔。
